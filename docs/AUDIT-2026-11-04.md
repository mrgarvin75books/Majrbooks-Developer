## 2. Architecture

- **Data access.** About 100 page components each query Supabase directly. There is no service, repository or domain layer, so business logic (posting, report math) lives inside React components.
- **Security model.** Postgres RLS is the only real security boundary. Route guards (`ClientRouteGuard`) are redirect-only.
- **Tenancy.** Each tenant is a single auth user: rows are keyed `user_id = auth.uid()`.
  - A "firm" is just the owner's user id.
  - "Clients" are CRM rows (`clients.user_id` = firm).
  - **The ledger tables (`chart_of_accounts`, `journal_entries`, `transactions`, `bank_transactions`, `invoices`) have no client or business column.** A firm keeping books for several clients therefore puts all of them into one ledger.
- **Roles: three systems that don't connect.**
  - `app_user_roles` (`admin`/`user`/`client`), which drives the UI.
  - `team_members.role` (`admin`/`accountant`/`employee`) plus `module_access`, which is UI-only.
  - `user_roles`, a QuickBooks-style catalog that is unused.
- **Navigation.**
  - `Layout.tsx` (~1,100 lines) has a staff sidebar plus a duplicate "Your Books" block.
  - Clients have two different menus: `ClientLayout.tsx` and the client branch in `Layout.tsx`.
  - Admins have `AdminSidebar.tsx`.
  - `App.tsx` defines 97 routes.

## 4. Functional modules: what actually works

### Works (real data, mostly correct)
- **Auth:** sign up, sign in and password reset.
- **Invoices:** create, edit, line items, recording payments, recurring generation and email send.
- **Invoice ledger posting.** DB triggers post balanced Dr AR / Cr Revenue on issue and Dr Cash / Cr AR on payment.
- **Manual journal entries:** create and view, with a UI-only balance check.
- **Transactions:** CRUD and Excel import on the single-entry `transactions` table.
- **Bank reconciliation matching:** CSV import into `bank_transactions` and matching.
- **Client invitations, team invites and the 14-day trial trigger.**
- **Firm-level data isolation.** All ledger tables use `auth.uid() = user_id`, and the audit found no way for one firm to read another firm's books.
- **Audit log** table (append-only).

### Partially works
- **Chart of Accounts.** CRUD works, but balances are numbers the user types in rather than values derived from the ledger. There are two clashing account-type vocabularies: Asset/Income vs Bank/Expenses/COGS.
- **General Ledger.** Mixes single-entry `transactions` with JE lines and shows one running balance across all accounts. Its account filter does nothing.
- **Journal Entry report.** Running balances ignore normal balance, so income, liability and equity accounts show negative.
- **Sales Tax Summary.** Counts drafts, estimates and cancelled invoices. Its export buttons do nothing.
- **Dashboards.**
  - Revenue = `max(transactions, invoices)`.
  - Cash is the sum of typed-in balances.
  - Drafts are counted as invoiced.
  - A user who is also a client of another firm sees that firm's invoices counted as their own revenue.
- **Stripe.** Checkout and the customer portal work. `check-subscription` crashes for **active paid** subscriptions because `current_period_end` was removed in API version `2025-08-27.basil`.

### Broken or placeholder
- **Trial Balance:** built from typed-in balances, and the date can't be changed. **Critical.**
- **Balance Sheet:** typed-in balances; ignores the selected date; drops AR, AP, inventory, credit cards and "Bank"-typed accounts; has no retained earnings; never checks that it balances. **Critical.**
- **Profit & Loss:** reads only single-entry `transactions` and ignores invoices and JEs. Sections are guessed from keywords in descriptions. **Critical.**
- **Cash Flow:** starting cash is the sum of all income minus all expenses ever recorded, and sections are guessed.
- **Expenses → Bills tab.** It reads and writes **`invoices`**, so every vendor bill becomes a customer receivable and **posts revenue** (`src/pages/Expenses.tsx:295`). **Critical.**
- **Quick Add Expense** inserts a negative amount, which violates `CHECK (amount > 0)`, so it **always fails** (`QuickAddExpenseDialog.tsx:48`). Quick Add Credit has the same problem.
- **Estimates and proposals** are stored as draft invoices. They pollute invoice lists, dashboards and the sales-tax report.
- **Bills** (`bills` table): no ledger posting.
- **Bank linking.** There is no Plaid; **three hardcoded fake accounts with fake balances are saved as "connected"**.
- **Import Transactions dialog:** uploads the file only. Nothing is parsed or created.
- **In-page reconciliation on BankTransactions:** the state is never saved, and "Finish" only shows a toast.
- **Standard Reports:** about 60 hardcoded report names whose menu actions do nothing. Neither AR Aging nor Client Statement exists.
- **Reports export:** shows a toast; no file is produced.
- **Multi-Entity:** "Create Group" does nothing, the counts are hardcoded, and there is no entity switching.
- **Expenses page:** Purchase Orders are mock data, and vendors and mileage live in React state only.
- **BookkeepingDashboard:** "pending reviews" is invented as 30% of the client count.
- **Navigation:** broken links (`/payroll` returns 404; staff "AI Support" and client "Training" redirect away). Several pages are duplicated: Dashboard/FinancialDashboard/Bookkeeping, Expenses/ExpenseTracking, Transactions/BankTransactions, Reports/StandardReports.

## 5. Accounting integrity problems

1. **There is no single general ledger.** Three record systems don't reconcile with each other:
   - single-entry `transactions`;
   - double-entry journals, used only by invoices, payments and manual JEs;
   - typed-in account balances.

   Each report reads from a different one. **No financial statement is derived from a balanced ledger.**
2. **The database doesn't enforce debits = credits.** It also has none of the following:
   - non-negative or one-side-only line checks;
   - immutability for posted entries (lines can be edited or deleted freely);
   - uniqueness for entry numbers.
3. **Manual JEs are posted non-atomically.** The header and the lines are two separate client inserts, so a failure between them leaves an orphaned "posted" header.
4. **No reversals or voids; hard deletes everywhere.**
   - Deleting an invoice cascades to its payments but leaves both auto-posted JEs behind, so AR and Revenue stay overstated.
   - Editing or cancelling an invoice after posting never adjusts its JE.
   - Transactions are hard-deleted.
5. **Sales tax is credited to Revenue.** There is no sales-tax liability, and tax isn't rounded.
6. **Deleting an account cascade-deletes its bank transactions.**
7. **Reconciliation:**
   - Bank and ledger rows are paired by selection order with no amount or date check.
   - There is no statement balance, period or lock.
   - Updates are three non-atomic calls.
   - The CSV parser breaks on quoted values such as `"$1,234"`.
8. **Imports:**
   - No duplicate detection.
   - Signs are dropped (`Math.abs`), so deposits become expenses.
   - Partial imports are left behind on failure.
9. **Money math:**
   - `parseFloat` and float `reduce` sums everywhere.
   - Dates in `YYYY-MM-DD` form are parsed as UTC, so the 1st of a month shifts into the previous month in US timezones.
10. **Silent truncation.** No query paginates, so above PostgREST's 1,000-row cap, reports quietly drop data.

## 6. Security problems (ranked)

**Critical**
- **`send-team-invite` edge function.** It runs with the service role, has no caller or owner check, and rewrites the invite token for any `teamMemberId`, then emails the link to an address the caller chooses. That lets anyone hijack a pending team seat.
- **Clients no longer get the `client` role [verify live].** Migration `20260226155834` replaced `handle_new_user_app_role` and dropped the `is_client` branch. Invited clients therefore become `user`: they see the full staff UI and pass `requireStaff`. In addition, `usePermissions` fails open (no `team_members` row means admin).
- **Billing gating is off for every paying customer.** `isStaff = role === 'user'` (`AuthContext.tsx:318`), and every self-signed-up owner is `user`. The paywall, trial banner, expiry modal and plan selection are therefore all skipped.

**High**
- **`invoice_payments` INSERT doesn't check invoice ownership,** and a SECURITY DEFINER trigger then updates the invoice. Any user who knows an invoice UUID can mark another firm's invoice paid.
- **`support_tickets` leak and can be forged.** SELECT allows `user_id IS NULL`, so all logged-out tickets (name, email, message) are readable by anyone. INSERT is `WITH CHECK (true)`.
- **Unauthenticated, service-role edge functions:**
  - `send-invoice`: emails any invoice and changes its status.
  - `analyze-receipt`: SSRF, and it can overwrite any receipt row.
  - `send-client-invitation` and `send-login-notification`: an open email and phishing relay with HTML injection.
- **Anyone can register as a client of any firm** with `/accept-client-invite?firm=<uuid>`, even without an invitation.
- **Users can extend their own trial forever.** The `profiles` UPDATE policy covers `trial_ends_at`, and the client writes it directly.
- **Firm owners can't reach Team, User Permissions or Billing.** Those routes are gated to the two hard-coded platform admins.
- **No Stripe webhook.** Subscription state is never persisted, and the trial check overrides paid status.

**Medium**
- **Invite RPCs (`accept_team_invite`, `mark_invitation_used`)** are granted to `anon` and trust a caller-supplied user id.
- **`accrue_pto_for_payroll`** is SECURITY DEFINER and trusts its `p_user_id` argument.
- **Cross-tenant foreign keys.** Lines, bank transactions and tasks can reference another tenant's accounts or employees.
- **Admin role is granted by email address in a trigger** at signup, before email confirmation.
- **The public `assets` bucket accepts uploads from any authenticated user** anywhere.
- **Publicly triggerable jobs.** The cron functions (`generate-recurring-*`, `check-overdue-invoices`) and `setup-storage` have `verify_jwt=false` and no shared secret.
- **AI functions:**
  - SSRF via the `fileUrl` parameter.
  - `schedule-c-analyze` is an open AI proxy that anyone can use to run up cost.
- **`create-checkout` trusts a client-supplied `priceId` and `withTrial`,** so trials can be repeated.
- **Team members see empty books.** Only 2 pages use `getScopeOwnerId`, and no RLS policy grants team members access to the owner's data.

**Low**
- `ANTHROPIC_API_KEY` sits in the frontend `.env`. It isn't bundled, but it belongs in Supabase secrets only.
- `vercel.json` sets no security headers.
- Every edge function sends a wildcard CORS header.
- The `TaxMajrAiLogin` page is a fake login that accepts any password.

Secrets: the frontend uses only the publishable key, and no service-role key or Stripe secret was found in `src/`.

## 8. Recommended improvements

1. **Make the journal the only source of truth.**
   - Every money event (income, expense, bill, bill payment, bank transaction, transfer, invoice, payment, payroll) posts through one server-side `post_journal_entry` RPC.
   - That RPC is atomic, checks debits = credits with a deferred constraint, is idempotent via a source key, and runs in a database transaction.
   - Posted entries become immutable. Corrections are made by reversal.
   - Every report reads from `journal_entry_lines`.
2. **Introduce a real business/entity tenancy key.**
   - Add a `businesses` (entity) table and an `entity_id` on all books tables.
   - Add an `entity_members` table (user × entity × role) for owners, accountants and client users.
   - Rewrite RLS around `is_entity_member(entity_id, min_role)`.
   - Keep `clients` as the firm's CRM view, linked 1:1 to an entity.
   - Contacts (people) stay separate from entities.
   - This one change delivers multi-entity, accountant access, client access and isolation together.
3. **Consolidate the role systems.**
   - Platform role (`admin`/`user`) stays in `app_user_roles`.
   - Per-entity role (`owner`/`accountant`/`staff`/`client`) moves to `entity_members`.
   - Retire `user_roles`, and make `isStaff` mean "is a team member".
4. **Add proper master data.** `customers` and `vendors` tables, a separate estimates document type, account `code`, `parent_id`, `normal_balance` and a fixed account-type taxonomy (QuickBooks-like), and `accounting_periods` with close/lock.
5. **Billing:**
   - A Stripe webhook that persists subscription state to a `subscriptions` table.
   - A server-side price allowlist.
   - `trial_ends_at` that users can't modify.
6. **Engineering:**
   - Vitest with accounting-engine tests. pgTAP or SQL tests for RLS and posting.
   - Integer-cents or decimal money helpers.
   - Date-only helpers.
   - Pagination.
   - Route-level code splitting.
   - Fix the 5 TypeScript errors.

## 10. Critical risks before modifying anything

1. **Live DB drift.** `clients`, `documents` and two buckets exist only in the live DB, and the deployed versions of functions may differ from the migrations. **Before any migration, I need either a schema dump (`supabase db dump --schema public`) or confirmation that I can run `supabase db pull` / link the project.**
2. **Production data.** Phase 3 backfills real client books. It needs a database backup or PITR snapshot and a staging project (or Supabase branch) to rehearse against. Please confirm whether a staging environment exists.
3. **Lovable two-way sync.** The repo is connected to Lovable. Edits made in Lovable while this work is in progress will conflict. I recommend freezing Lovable edits, or working on a branch.
4. **Existing reports will change.** Once reports read from the ledger, current users' P&L and Balance Sheet figures will differ, because today's figures are wrong. Plan to tell clients.
5. **Breaking role changes.** Fixing the client role and `isStaff` changes what existing users see immediately. That is the correct behaviour, but it is visible.
6. **No tests exist.** Every phase needs its own test harness built first, so estimates should include that work.
7. **Design reference.** The brief mentions an uploaded screenshot, but none came through in this conversation. Please attach it before Phase 2.
